# Raft Integration Work Plan

Requested scope: implement items 1 through 7 so the shard replication path uses
Raft-backed commit semantics.

1. Raft shard consensus implementation
   - Added database-internal `RaftShardConsensus` lifecycle over one `RaftCore`
     per shard.

2. Shard-level RaftCore lifecycle
   - Raft groups are opened from the existing shard WAL and commit stores.
   - Static routing primaries bootstrap as Raft leaders for cluster server mode.

3. RequestVote and AppendEntries RPC
   - Added TCP replication-port handling for Raft AppendEntries and RequestVote.
   - Added client helper for RequestVote RPC.

4. Election and heartbeat loop
   - Added server heartbeat loop that sends Raft commit heartbeats over the
     replication transport.
   - Added election rounds that send RequestVote RPCs and promote candidates
     when vote quorum is reached.
   - Added leader-contact tracking on AppendEntries/heartbeat and timeout-based
     election suppression with server-id jitter.

5. Durable Raft log
   - Reused the existing segmented shard WAL as the durable Raft log.
   - Reused the existing commit store as the durable commit index.

6. Commit-only apply
   - Raft transport followers append entries without applying them immediately.
   - Graph state is applied only after leader commit advances.

7. Membership
   - Routing table changes rebuild the per-shard Raft voter sets.
   - RaftCore now supports joint consensus quorum checks for old and new voter
     sets, and routing table changes pass through the joint membership model
     before rebuilding final shard voters.

Additional Raft hardening:

- Strong reads in Raft mode now require local Raft read-index validation.
- Followers reject default strong reads unless they are the local Raft leader;
  callers can explicitly use follower-stale reads when serving replica data.
- Routing-table installs now append a durable `ClusterConfigChange` command to
  the replicated shard log.
- Raft leaders now refresh a short leader lease after quorum confirmation and
  strong reads use that lease before falling back to read-index validation.
- Remaining work: enforce production clock-bound assumptions for leases and
  apply replicated configuration-change commands as cluster metadata state
  transitions instead of treating them as no-op materialized graph commands.
